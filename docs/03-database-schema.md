# SAHL — Database Schema (Draft v1)

Status: Draft — implements the bounded contexts from [02-architecture.md](02-architecture.md). Executable draft lives in [`apps/backend/prisma/schema.prisma`](../apps/backend/prisma/schema.prisma). This document explains the *why* behind the modeling choices; the schema file is the source of truth for fields/types.

## 1. Modeling Conventions

- **Money**: always `Int` minor units + a `currency` (ISO 4217) column. Never `Float`/`Decimal` for currency without minor-unit convention — avoids rounding bugs at scale.
- **IDs**: `cuid()` everywhere (sortable-ish, collision-safe without a central sequence — matters once there's more than one write node).
- **Soft state, not deletion**: user-facing entities use status enums + timestamps (`cancelledAt`, `suspendedAt`) rather than hard deletes, to preserve audit trail and referential integrity for payments/contracts.
- **Translations**: category/taxonomy names go through a `*Translation` join table keyed by locale, per [ADR-001](02-architecture.md#adr-001-locale--payment-abstraction) — never `nameEn`/`nameAr` columns, which don't scale past 2 languages and duplicate logic per-field.
- **One identity, dual role**: `User` is never typed `CUSTOMER` vs `PROVIDER`. Every `User` can act as a customer; `ProviderProfile` is an optional 1:1 extension activated on demand. Staff roles (Admin, Support, etc.) are a separate RBAC concern layered on top, not a `role` enum on `User`.

## 3. Key Relationships & Rationale

- `ServiceCategory.type` (`ON_DEMAND | CONTRACT | REMOTE`) determines which request-type table a category is valid for; enforced at the application layer (Postgres can't easily cross-validate this without a trigger, and a trigger would hide the rule from the codebase — so the use case validates it).
- `OnDemandRequest` → `OnDemandAssignment` is 1:N (multiple providers can be offered the job in sequence/parallel per the matching engine) but only one `ACCEPTED` assignment at a time — enforced in application logic, not a DB constraint, because the "only one active" rule is a business rule likely to gain exceptions (e.g. multi-provider jobs) that shouldn't require a schema migration to relax.
- `ContractProject` → `ContractBid` (N) → exactly one accepted bid promotes to a `Contract`. `ContractBid` is kept even after acceptance/rejection for audit and provider bidding-history analytics (feeds matching engine's provider track record).
- `ContractMilestone` and `RemoteMilestone` are separate tables rather than a shared polymorphic `Milestone` table — Contract and Remote milestones have diverging fields (Contract needs site-inspection sign-off fields later; Remote needs revision-count fields) and a shared polymorphic table would force nullable columns per divergence. Revisit if/when the fields converge.
- `PaymentTransaction.relatedEntityType/relatedEntityId` is a polymorphic reference (on-demand request, contract, remote engagement, milestone, escrow, withdrawal, subscription) rather than seven nullable FKs — payments are inherently cross-cutting and a single ledger table is required for financial reconciliation. See [ADR-008](02-architecture.md#12-adr-008-financial-core-double-entry-ledger-architecture) for the full Financial Core design (this table is now the customer/provider-facing half of it; `JournalEntry`/`JournalLine` is the accounting half).
- `MatchingScoreLog` persists computed scores + the factor breakdown (JSON) per ranking run — not for the live request path (that's Redis-backed, see [06-smart-matching.md](06-smart-matching.md)), but so the algorithm's decisions are auditable and usable as training data later (Future AI Features in the brief).
- `Region` + `PaymentGatewayConfig` implement [ADR-001](02-architecture.md#adr-001-locale--payment-abstraction): every money-relevant or locale-relevant row carries a `regionId` (directly or via the owning user), so multi-country support is a data dimension, not a code fork.
- `OnDemandRequest.fulfillmentMode` + `scheduledFor` implement Scheduled Service as a booking mode rather than a new context, per [ADR-003](02-architecture.md#7-adr-003-scheduled-service-is-a-booking-mode-of-on-demand-not-a-fourth-bounded-context). `ProviderAvailabilitySlot` exists specifically to make future-time availability queryable for scheduled matching, distinct from the live `ProviderProfile.isAvailable` flag used for instant dispatch.
- `Dispute` (transactional, tied to a specific paid engagement, resolved by Finance/Support staff) and `Report` (trust & safety flagging of a provider/review/message, resolved by Moderation) are kept as separate models rather than one generic "flag" table — they have different resolution workflows, different staff-role owners ([04-api-modules.md](04-api-modules.md) §3), and conflating them would force one workflow to accommodate the other's fields.
- `ReferralRedemption.redeemedById` is `@unique` — a user can redeem at most one referral code, enforced at the DB level (not just application logic) because it's a hard business invariant with a fraud-prevention purpose, unlike the softer rules noted above that are deliberately left to the application layer.
- `Company`/`CompanyMember` wrap existing `User`s rather than introducing a second identity type, per [ADR-004](02-architecture.md#8-adr-004-businesscompany-accounts-extend-identity-they-dont-fork-it). `ProviderProfile.companyId` and the `companyId` added to `OnDemandRequest`/`ContractProject`/`RemoteEngagement` are additive, nullable columns — a personal request/provider profile is completely unaffected by the existence of companies.
- `Wallet` moves from `userId @unique` (required) to `userId @unique` (optional) + `companyId @unique` (optional) to support company wallets. Exactly one must be set — the same app-validated convention as `PaymentTransaction`'s polymorphic reference, not a new pattern.
- `Coupon` (code-redeemed, per-user, e.g. "SAVE20") and `PromotionalCampaign` (automatic, category-wide, no code) are separate models because a customer discovers and applies them completely differently, even though both ultimately reduce a charge — conflating them would mean every read path has to branch on "does this have a code."
- `ReviewCategoryScore` is a normalized child table keyed by a fixed `ReviewCategory` enum (Professionalism/Communication/Quality/Punctuality/Value) rather than JSON on `Review`, because these sub-ratings need per-dimension aggregation (e.g. a provider's average "Punctuality" score) — something JSON columns don't index or `AVG()` cleanly in Postgres.
- `ProviderWorkingHours` (recurring weekly template, minutes-from-midnight) is distinct from `ProviderAvailabilitySlot` (specific future bookable instances, ADR-003) — working hours answer "is this provider open right now" for search filtering; availability slots answer "can I book this provider at 3pm next Tuesday" for scheduled matching. Conflating them would force every "open now" search to reason about scheduling-slot semantics it doesn't need.
- `TransactionStatus.HELD` marks an individual transaction as captured-but-not-yet-released; the actual escrow lifecycle (partial release, dispute, expiry) is tracked on the dedicated `Escrow` model, not by branching on this status — see [ADR-008](02-architecture.md#12-adr-008-financial-core-double-entry-ledger-architecture), which superseded an earlier draft of this note that conflated the two.
- `SearchQueryLog` exists solely to power "recent searches" and "popular searches" — the searches themselves query existing tables (`ServiceCategory`, `ProviderProfile`, geo/PostGIS) directly; this table has no role in executing a search, only in remembering that one happened.
- `targetingRules Json` on `RemoteConfigEntry`, `HomeLayoutBlock`, `NotificationBroadcast`, `PopupCampaign`, and `Advertisement` is the *same* shape everywhere (`packages/shared/schemas/targeting.schema.ts`), not five bespoke targeting schemas — see [ADR-007](02-architecture.md#11-adr-007-admin-panel-as-platform-control-center) §1. It's a rule blob, not a normalized many-to-many audience table, because the criteria are heterogeneous boolean combinations (country AND role AND category) better suited to rule evaluation at the application layer than relational joins.
- `RemoteConfigEntry` is deliberately narrow in scope — typed key-value for settings with no natural relational shape (OTP expiry, rate limits, maintenance mode, app version gates). `CommissionRule`, `PromotionalCampaign`, `Coupon`, and `AiFeatureToggle` are **not** migrated into it despite being "configuration" in the business sense — they already have proper relational shapes (a `categoryId` FK, their own discount fields, a capability enum) that a generic key-value row would flatten and lose type safety on. See ADR-007 §3.
- `MessageTemplate` unifies what the source specs list as three separate asks — "Email Templates," "SMS Templates," "Notification Templates" — behind one `channel` enum, because the shape (keyed template, per-locale subject/body, `{{variable}}` placeholders) is identical across all three. See ADR-007 §4.
- `PublishStatus.ARCHIVED` is the soft-delete mechanism for `CmsPage`, `HomeLayoutBlock`, `PopupCampaign`, and `NotificationBroadcast` — no separate `deletedAt` on those, since it would be redundant state to keep in sync with the status enum. Entities in this section without a lifecycle status of their own (`RemoteConfigEntry`, `MessageTemplate`) get an explicit `deletedAt` instead.
- `Wallet.balance` was removed — see [ADR-008](02-architecture.md#12-adr-008-financial-core-double-entry-ledger-architecture). Balances live in `WalletBalance` (per wallet, per `WalletBucket`), and the ledger (`LedgerAccount`/`JournalEntry`/`JournalLine`) — not the wallet row — is the source of truth. `WalletBalance` is a subsidiary ledger rolling up into GL control accounts (`CUSTOMER_WALLETS_PAYABLE`/`PROVIDER_WALLETS_PAYABLE`), not a second independent balance to keep in sync by hand.
- `PaymentTransaction.journalEntryId` is `@unique` (one transaction, one balanced entry) — a business event that splits money multiple ways (e.g. an escrow release into provider share + platform commission) is multiple `PaymentTransaction` rows, each with its own independently-balanced `JournalEntry`, never several transactions sharing one entry. See `application/finance/release-escrow.use-case.ts` for the worked example.
- `Payout` was renamed to `Withdrawal` and extended with an approval workflow, `method`, and fee — done as a clean rename (no live data existed) rather than building a second, parallel "Withdrawal" concept alongside the pre-existing `Payout`, which would itself have been the duplicated-logic anti-pattern this schema avoids elsewhere.
- `Settlement` groups many `Withdrawal` rows for platform-side batch processing; it is not a `TransactionType` value — see ADR-008's consolidation of the source spec's 19 transaction types down to 17 (also folding "Partial Refund" into `REFUND` with a smaller amount, not a separate type).
- `DomainEvent.type` and `WorkflowDefinition.triggerEventType` are free strings, not closed enums — same convention as `PaymentGatewayConfig.provider`/`AiProviderConfig.provider` — because the event/workflow vocabulary is expected to grow routinely and a closed enum would need a migration per new event. See [ADR-009](02-architecture.md#13-adr-009-workflow-engine-as-a-cross-entity-orchestration-layer).
- `WorkflowDefinition`/`WorkflowStep`/`WorkflowInstance`/`WorkflowStepExecution`/`AutomationRule` orchestrate *between* the entity state machines already listed throughout this document (`OnDemandStatus`, `ContractStatus`, `EscrowStatus`, `WithdrawalStatus`, `SubscriptionStatus`, `DisputeStatus`, ...) — they do not replace any of them. `WorkflowInstance.definitionVersion` is a snapshot at start time, so republishing a `WorkflowDefinition` never changes the behavior of instances already running. See ADR-009 and [10-workflow-engine.md](10-workflow-engine.md).
- `WorkflowActionType` was consolidated from the source spec's 17 action types to 14 (`SEND_NOTIFICATION`/`SEND_EMAIL` → `SEND_MESSAGE` parameterized by the existing `MessageChannel`; `TRIGGER_WEBHOOK`/`CALL_EXTERNAL_API` → one `CALL_EXTERNAL_API`) — same consolidation discipline as the Financial Core's transaction types.

## 4. Deferred / Not Yet Modeled

These are intentionally left out of v1 rather than guessed at:

- Fraud-detection feature tables (Future AI Feature — needs a defined signal set first).
- ~~Subscription/premium-listing tables~~ — resolved this round: `SubscriptionPlan`/`Subscription` (see [ADR-008](02-architecture.md#12-adr-008-financial-core-double-entry-ledger-architecture)). Still Phase 2 to *activate* (`SubscriptionPlan.isActive`), same off-by-default convention as `CommissionRule`/`PromotionalCampaign`.
- A dedicated `Invoice` entity — `ContractMilestone`/`RemoteMilestone.status` (`PAID`) plus `PaymentTransaction` already capture what's owed and what's been paid; a formal invoice document (PDF generation, invoice numbering) is a presentation/reporting concern layered on that data, not new domain state, unless a real invoicing requirement (e.g. tax compliance) emerges.
- Video meeting provider-specific fields in `RemoteMeeting` (blocked on the open question in ADR section 10 of the architecture doc).
- FAQs now have a home in `CmsPage` (type `FAQ`, `HELP_CENTER`) per [ADR-007](02-architecture.md#11-adr-007-admin-panel-as-platform-control-center) — the "likely a lightweight CMS" note from an earlier round is resolved. Feature-request & bug-report intake is still deferred — that's product-feedback tooling, not content, and a third-party tool remains a reasonable alternative to bespoke tables when Support Center is built.
- Dynamic Forms (per-category custom service-request intake fields), Pricing Templates, and Contract Templates — all named in "Marketplace Management" (ADR-007) but need field-type/validation/conditional-logic design shaped against a real category's requirements, not guessed at speculatively ahead of one. See ADR-007's deferred note.
- A true A/B-testing statistics engine — `HomeLayoutBlock.abTestGroup` is a label an admin sets manually, not a system that computes statistical significance or auto-allocates traffic. Build that only if simple manual group labeling turns out to be insufficient.
- Provider Insurance and social login (Google/Apple) — both explicitly marked "future" in the source specs; no schema until the actual requirement (what insurance data, which OAuth provider) is known.
- Biometric authentication (Face ID/fingerprint) — a client-side credential concern (device secure enclave), not a schema change; the API side is unaffected since it still receives the same JWT/refresh-token flow.
- A real payment gateway adapter (`infrastructure/payments/<gateway>/`) — `domain/payments/payment-provider.ts`'s interface was specified in ADR-001 but a concrete implementation needs a selected gateway (still an open item in [07-roadmap.md](07-roadmap.md)); building one against a guessed wire protocol isn't worth doing twice.
- A per-user/per-event-sourced `WalletBalance` read model — only justified if reading current bucket balances becomes a measured performance problem (ADR-008's revisit trigger), not built speculatively.
- International withdrawal provider types beyond bank transfer/wallet transfer/mobile money — `WithdrawalMethod` is a fixed enum for now; if "Future International Providers" becomes concrete, revisit whether it should become a registry-resolved free string like `PaymentProvider`/`AIProvider` instead (see [09-financial-core.md](09-financial-core.md) §10).
- The `conditionExpression` rule evaluator, per-`AutomationRule` scheduled-scan jobs, and 11 of 14 `WorkflowActionType` executors — schema-complete, not code-complete; see [10-workflow-engine.md](10-workflow-engine.md) §7 for the full list and why each is scoped to when it's actually invoked rather than built speculatively.
